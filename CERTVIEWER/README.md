# Сертвивер — реестр сертификатов

Модуль административной платформы: хранит сертификаты сотрудников, разбирает
PEM/DER и показывает ФИО, идентификатор (СНИЛС/ИНН) и срок действия.

Обычный режим работы — **в составе платформы** (`helpdesk-backend`): модуль
слушает только `127.0.0.1:3101`, снаружи недоступен, а вход и роль проверяет
платформа до того, как запрос дойдёт сюда. Пункт «Сертвивер» появляется в
сайдбаре у роли `it`.

Автономный режим (без платформы, со своим логином) сохранён — см. ниже.

## Установка

Требуется Node.js 22.13+ (используется встроенный `node:sqlite`).

```bash
npm install
cp .env.example .env
```

Все зависимости чистые, без нативных C++-модулей — компилятор и Visual Studio
не нужны ни при какой версии Node.

## Настройка

Значения задаются в `.env` (в репозиторий не коммитится, см. `.env.example`).

| Переменная | Назначение |
|------------|------------|
| `PORT` | порт модуля, по умолчанию **3101** (в платформе прописан этот же — см. `helpdesk-backend/config/modules.js`) |
| `BEHIND_GATEWAY` | `true` — работа за платформой, `false` — автономно |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | логин и пароль собственного входа, нужны только при `BEHIND_GATEWAY=false` |
| `SESSION_SECRET` | секрет подписи сессионной cookie |

**За платформой (`BEHIND_GATEWAY=true`)** — рекомендуемый режим:
модуль слушает только `127.0.0.1`, собственный вход по паролю отключён
(`POST /login` отвечает отказом), доступ полностью определяется платформой.

**Автономно (`BEHIND_GATEWAY=false`)** — модуль слушает сеть и проверяет вход
сам, поэтому `ADMIN_PASSWORD` **обязателен**: без него сервер не запустится и
напишет, что делать. Значения пароля по умолчанию нет специально — иначе
реестр оказался бы доступен из сети с общеизвестным паролем, если `.env`
забыли создать.

Если не задать `SESSION_SECRET`, модуль возьмёт случайный секрет на время
работы процесса: подделать сессию нельзя, но после каждого перезапуска
придётся входить заново. Для постоянной работы задайте своё значение.

## Запуск

```bash
npm start
```

Автозапуск как служба Windows через NSSM:

```
nssm install CertViewer "C:\Program Files\nodejs\node.exe" "C:\apps\certviewer\server.js"
nssm set CertViewer AppDirectory "C:\apps\certviewer"
nssm start CertViewer
```

## Данные

Всё хранится в одном файле `certificates.db` (SQLite) рядом с `server.js`.
Для резервной копии достаточно скопировать этот файл.

Модуль SQLite (`node:sqlite`) встроен в сам Node.js начиная с 22.13 —
npm-пакетов и компиляции не требуется, вопрос с Visual Studio / node-gyp не
возникает независимо от версии Node на сервере. При запуске Node печатает
`ExperimentalWarning: SQLite is an experimental feature` — это не ошибка,
программа работает штатно.

Уникальность записи — по паре «эмитент + серийный номер сертификата»: это
настоящий идентификатор в X.509, в отличие от ФИО или СНИЛС, которые
повторяются при перевыпуске сертификата на того же сотрудника.

## Формат сертификатов

Поддерживаются PEM (текстовый, начинается с `-----BEGIN CERTIFICATE-----`) и
DER (бинарный, обычно `.cer`/`.crt`), не больше 5 МБ и до 50 файлов за раз.
Извлекаются:

- **ФИО** — из атрибутов Surname/GivenName, либо из Common Name, если их нет;
- **Идентификатор** — из атрибута subject `serialNumber` (СНИЛС/ИНН на
  квалифицированных сертификатах), либо серийный номер самого сертификата;
- **Срок действия** — `notBefore` / `notAfter`.

Разбор сделан на `@fidm/x509`, а не на node-forge: forge пытается разобрать
сам открытый ключ и падает с «OID is not RSA» на сертификатах КриптоПро с
ГОСТ Р 34.10.

Если у какого-то УЦ структура полей отличается и данные извлекаются не в те
колонки — логику разбора в `parseCertificate()` (`server.js`) нужно дополнить
под конкретный формат.
