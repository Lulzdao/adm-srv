# Платформа: служба заявок и хост встроенных модулей

Ядро административной платформы: Node.js + Express + встроенный `node:sqlite`.
Отвечает за вход (LDAP в двух доменах), роли, заявки — и за то, чтобы
встроенные модули (Сертвивер, Журнал звонков) были доступны только вошедшим
пользователям с нужной ролью.

Это единственная часть системы, которую видно из сети. Модули слушают
`127.0.0.1` и снаружи недоступны — запросы к ним идут только через прокси
платформы, после проверки входа и роли.

**Требуется Node.js 22.5+.** Используется встроенный модуль `node:sqlite`
вместо `better-sqlite3`: последний — нативный C++-аддон, которому нужен либо
готовый бинарник под конкретную версию Node/ОС, либо сборка на месте через
node-gyp с интернетом и build-инструментами, чего в закрытом контуре нет.
`node:sqlite` — часть самого Node.js, собирать нечего.

При запуске Node печатает `ExperimentalWarning: SQLite is an experimental
feature` — это ожидаемо и работе не мешает.

## Отделы и роли

Заявка привязана к отделу (ИТ / ХОЗ / ЕГРПО) — от этого зависит номер
(ИТ-0001, ХОЗ-0001, ЕГРПО-0001, у каждого отдела свой счётчик) и кто получит
уведомление о новой заявке.

Видимость заявки:

| Роль | Что видит | Что может менять |
|------|-----------|------------------|
| `it` | все заявки всех отделов | любую заявку |
| `hoz`, `egrpo` и т.п. | очередь своего отдела + собственные заявки в любом отделе | заявки своего отдела |
| `user` | только свои заявки (созданные или назначенные на него) | ничего (только создать заявку и комментировать) |

Право **видеть** заявку и право её **менять** — разные вещи: заявитель видит
свою заявку и может её комментировать, но сменить статус, приоритет или
исполнителя может только ИТ или исполнитель профильного отдела.

Роль назначается по членству в AD-группе — своя группа на каждый отдел и на
каждый домен, настраиваются в разделе «Администрирование» (доступен только
роли `it`). Имя группы сравнивается с первым компонентом DN (`CN=...`)
целиком: группа `Otdel-IT` — это ровно `Otdel-IT`, а не `Otdel-IT-Praktikanty`.

Добавить новый отдел — один объект в `config/departments.js`; категория в БД,
маршрутизация уведомлений, права, выпадающие списки и блок настройки AD-группы
появятся сами при следующем старте.

## Быстрый старт

```bash
npm install
cp .env.example .env
```

Заполните в `.env`:

- `SESSION_SECRET` — длинная случайная строка. **Задайте обязательно:** если
  переменной нет, сервер возьмёт случайный секрет на время работы процесса, и
  после каждого перезапуска всем придётся войти заново.
  Сгенерировать: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
- адреса контроллеров доменов А и Б (`DOMAIN_A_LDAP_URL`, `DOMAIN_B_LDAP_URL`) — лучше `ldaps://` (порт 636)
- `DOMAIN_A_SVC_DN` / `DOMAIN_B_SVC_DN` и пароли — сервисная учётка только на чтение
- `DOMAIN_A_ADMIN_GROUP` / `DOMAIN_B_ADMIN_GROUP` — точные названия групп ИТ-отдела в каждом домене

Локальный аварийный вход (на случай недоступности обоих доменов). Логин
**обязательно** начинается с `!` — по этому символу фронтенд отличает
локальный вход от доменного и не ищет такой логин в LDAP. Аккаунта два:
`!admin` (роль `it`) и `!user` (без прав администратора):

```bash
node scripts/set-local-admin-password.js "ВашНадёжныйПароль"
# вставьте выведенный хэш в .env как LOCAL_ADMIN_PASSWORD_HASH
node scripts/set-local-admin-password.js "ДругойПароль"
# вставьте в .env как LOCAL_USER_PASSWORD_HASH
```

Автоопределение домена по подсети клиента: `NETWORK_DOMAIN_A_CIDR` /
`NETWORK_DOMAIN_B_CIDR`. Экран входа не показывает вкладки выбора домена —
определяет его по IP запроса (`req.socket.remoteAddress`; заголовки вроде
`X-Forwarded-For` игнорируются, чтобы домен нельзя было подделать). Если
сервер окажется за reverse proxy, потребуется отдельно настроить `trust proxy`
и список доверенных источников.

Инициализация БД и запуск:

```bash
node db/init.js
npm start
```

Проверка: `curl https://localhost:3000/api/health` (или `http://`, если
сертификат не задан — см. следующий раздел).

## HTTPS

Шифрование включается само, как только задан сертификат, — отдельного
переключателя нет, чтобы не было состояния «сертификат положили, а включить
забыли». Ничего не задано — платформа работает по HTTP и предупреждает об этом
в консоли. Обратного прокси перед приложением нет намеренно: так не остаётся
параллельного незашифрованного порта, про который легко забыть. Ровно та же
схема у модуля «Искра» — настройка у обоих сервисов выглядит одинаково.

### Сертификат один на оба сервиса

Платформа и «Искра» стоят на одной машине и отвечают на одно имя —
`p48-srv-adm01.rosstat.local`, — поэтому сертификат у них **один**, и лежит он
в одном месте:

```
MESSENGER/certs/
  server.pfx        сертификат сервера (внутри закрытый ключ и цепочка)
  server.pass       пароль к нему: обычный текст, БЕЗ перевода строки в конце
  server.pfx.bak    копия, которую панель делает перед заменой
  server.pass.bak
```

Обе службы читают этот файл и **перечитывают его сами, когда он меняется** —
перезапуск не нужен: новые соединения идут с новым сертификатом, уже открытые
доживают со старым. Поэтому загрузить новый можно из любой панели: раздел
«Сертификаты» платформы или раздел «Сертификат» «Искры», разницы нет.

Путь к хранилищу меняется переменной `SHARED_CERT_DIR`.

Если новый файл окажется битым или с неверным паролем, он **не применяется**:
в консоль уходит «Новый сертификат не принят, оставлен прежний», и сервис
продолжает работать на старом. Испортить работающую платформу загрузкой не
того файла нельзя.

**Почему одного сертификата хватает на две подсети.** Подсети действительно
две — `10.148.12.0/22` (`rosstat.local`) и `192.168.254.0/23` (`in.local`), — но
имя у сервера одно. В `in.local` заведена запись на этот адрес и маршрут через
шлюз, который его знает, так что клиенты обеих подсетей обращаются по
`p48-srv-adm01.rosstat.local`. Второе имя, второй сертификат и выбор
сертификата по имени (SNI) не нужны. Удостоверяющий центр тоже один: его
корень раздаётся групповыми политиками в оба домена, и клиенты берут его из
хранилища Windows — ни от нашего сервера, ни от панели это не зависит.

### Как поставить сертификат сервера

Это единственное, что нужно делать с сертификатами в обычной жизни.

**1. Выпустить в УЦ домена.** Запрос по шаблону веб-сервера, в SAN —
`DNS:p48-srv-adm01.rosstat.local`. IP в SAN не нужен: и платформа, и клиенты
ходят по имени.

**2. Экспортировать в PFX** — обязательно **вместе с закрытым ключом и всеми
сертификатами пути**. В оснастке «Сертификаты»: правой кнопкой по сертификату
→ Все задачи → Экспорт → «Да, экспортировать закрытый ключ» → PFX → отметить
«Включить по возможности все сертификаты в путь сертификации». Пароль
задаётся там же. Без цепочки клиент может не достроить доверие — панель
показывает это отдельной строкой «Цепочка: неполная».

**3. Загрузить** — в разделе «Сертификаты» платформы или в разделе
«Сертификат» «Искры». Файл проверяется (пароль, срок, цепочка) и только потом
заменяет действующий; прежний остаётся с суффиксом `.bak`.

**4. Проверить** там же: кому и кем выдан, срок, полная ли цепочка.

Применяется на лету. Перезапуск нужен ровно в одном случае — **первая**
установка, когда служба поднялась по HTTP: превратить работающий HTTP-сервер в
HTTPS без перезапуска нельзя, и панель об этом пишет прямо.

### Установка сертификата без панели

Нужна, когда служба не поднимается и панель недоступна. Всё делается файлами в
`MESSENGER\certs\`, от имени администратора:

```bat
copy /Y C:\temp\server.pfx C:\adm-srv\MESSENGER\certs\server.pfx

rem Пароль — БЕЗ перевода строки в конце, иначе он не подойдёт.
rem Обычный echo дописывает \r\n, поэтому только такая форма:
echo|set /p="пароль-от-pfx" > C:\adm-srv\MESSENGER\certs\server.pass
```

PowerShell — то же самое, но там за перевод строки отвечает `-NoNewline`:

```powershell
Set-Content -Path C:\adm-srv\MESSENGER\certs\server.pass -Value 'пароль-от-pfx' -NoNewline
```

Если PFX без пароля — файла `server.pass` просто не должно быть.

Дальше: работающая служба подхватит файл сама в течение пары секунд. Если
служба была остановлена или работала по HTTP — перезапустить обе
(`net stop`/`net start` или через оснастку служб). В консоли платформы при
старте должно появиться `TLS включён: сертификат из …`.

Проверить, что реально отдаётся, не заходя в панель:

```powershell
# что предъявляет сервер и кому выдан
openssl s_client -connect p48-srv-adm01.rosstat.local:3000 -servername p48-srv-adm01.rosstat.local < NUL | openssl x509 -noout -subject -issuer -dates
```

### Как отключить HTTPS

Отдельного переключателя нет намеренно: он создал бы состояние «сертификат
положили, а включить забыли». Шифрование есть ровно тогда, когда есть
сертификат, — значит, выключается оно уборкой сертификата:

```bat
cd C:\adm-srv\MESSENGER\certs
ren server.pfx  server.pfx.off
ren server.pass server.pass.off
```

Затем **перезапустить обе службы**. На ходу HTTPS не выключается: работающий
HTTPS-сервер остаётся HTTPS-сервером до перезапуска — это ограничение Node, а
не решение с нашей стороны. После перезапуска обе службы поднимутся по HTTP и
напишут об этом в консоль и в журнал.

Важно: если сертификат задан **ещё и** переменными окружения (`TLS_PFX` или
`TLS_CERT`/`TLS_KEY`) в скрипте запуска или в настройках службы, уборка файлов
ничего не даст — платформа возьмёт сертификат оттуда. Тогда убрать нужно и
переменную. Панель «Искры» предупреждает о такой двойной настройке заранее.

Обратно — вернуть имена файлов и перезапустить.

### Явное указание сертификата

Если общее хранилище по каким-то причинам не подходит, сертификат задаётся в
`.env` — тогда он имеет приоритет над хранилищем, а слежение за файлом и
загрузка из панели отключаются: явный путь менять на ходу не наше дело.
Внимание, «Искра» в этом случае разойдётся с платформой — у неё приоритет
обратный (сначала файл в хранилище, потом переменные), так что на одной машине
службы предъявят разные сертификаты. Задавать здесь путь стоит, только если
файла в хранилище нет вовсе:

```bash
# PFX из УЦ домена — вместе с закрытым ключом и всеми сертификатами пути
TLS_PFX=C:\adm-srv\server.pfx
TLS_PFX_PASSWORD=пароль-от-файла

# либо PEM: TLS_CERT — обязательно ПОЛНАЯ цепочка, ключ без пароля
TLS_CERT=/etc/adm-srv/fullchain.crt
TLS_KEY=/etc/adm-srv/server.key
```

Битый файл или неверный пароль выясняются при запуске, а не при первом
обращении пользователя: сервер не поднимется и напишет, в чём дело.

Когда TLS включён, сессионная кука автоматически помечается `Secure` —
браузер не отправит её открытым текстом. По HTTP флаг не ставится: браузер
тогда не примет куку вовсе и вход перестанет работать.

**Про модули за HTTPS.** Платформа проверяет сертификат модуля
по-настоящему (`secure: true` в `routes/modules.js`), поэтому модуль в
`config/modules.js` должен быть адресован **именем из его сертификата**, а не
по `127.0.0.1`. В сертификате «Искры», например, записано только
`DNS:p48-srv-adm01.rosstat.local` — обращение по IP не пройдёт проверку имени,
и модуль не откроется. Корневой УЦ домена Node берёт из хранилища Windows
(приложение запускается с `--use-system-ca`); на машине вне домена корневой
сертификат указывают в `NODE_EXTRA_CA_CERTS`.

Если модуль не открывается, платформа отличает проблему с сертификатом от
обычной недоступности: в ответе будет «не удалось установить защищённое
соединение», а в консоли — код ошибки TLS и подсказка, что проверить.

### Раздел «Сертификаты» в панели

Доступен роли `it`. Разведён на две части намеренно — это разные сущности,
которые постоянно путают:

- **Сертификат сервера — что мы предъявляем.** Основная часть экрана и
  единственная, с которой работают регулярно: кому и кем выдан, имена в SAN, до
  какой даты, полная ли цепочка, отпечаток — и тут же загрузка нового (см.
  «Как поставить сертификат сервера»). Ниже — что предъявляет каждый модуль и
  проходит ли его сертификат строгую проверку: тот же вопрос, который решает
  прокси, только показанный заранее, а не в момент поломки.
- **Доверенные корни — кому верим мы.** Свёрнутый блок внизу, и это не
  случайно: он нужен редко. К клиентам он отношения **не имеет** — они берут
  корни из хранилища Windows, куда те приезжают групповыми политиками, и
  панель на это никак не влияет. Речь только об исходящих соединениях самой
  платформы: LDAPS к контроллерам доменов и проверка сертификата «Искры» при
  проксировании. Удостоверяющий центр у нас один, и на доменной машине здесь
  не нужно ничего: платформа запускается с `--use-system-ca` и доверяет тому же
  хранилищу Windows. Блок пригождается в двух случаях: машина вне домена и
  переходный период при смене УЦ. Файлы лежат в `helpdesk-backend/certs/trusted/` (путь меняется
  переменной `TRUSTED_CA_DIR`), подключаются переменной `NODE_EXTRA_CA_CERTS`
  и начинают действовать **после перезапуска** платформы: Node читает эту
  переменную один раз при старте, обойти это из кода нельзя. Панель об этом
  честно пишет при добавлении.

## Встроенные модули

Платформа проксирует запросы к модулям, каждый из которых — отдельный процесс
на своём порту `127.0.0.1`. Модули про вход ничего не знают: сессию и роль
проверяет платформа до того, как запрос уйдёт дальше.

Подключение нового модуля — одна строка в `config/modules.js`:

```js
{
  id: "certs", label: "Сертвивер", path: "/modules/certs",
  target: "http://127.0.0.1:3101", roles: ["it"],
  views: [{ id: "root", label: "Сертвивер", sub: "" }],
}
```

Дальше всё само: `routes/modules.js` поднимет прокси на `path` с проверкой
`requireAuth` + роли, а фронтенд получит модуль в `/api/modules` и добавит
пункт в сайдбар. Возвращаться в `routes/modules.js` не нужно.

Подключённые модули — см. корневой `README.md` репозитория.

## Структура

- `config/` — сборка конфига из `.env`, список отделов, реестр модулей
- `db/schema.sql`, `db/init.js` — схема SQLite и инициализация
- `services/ldapAuth.js` — LDAP-аутентификация (bind сервисной учёткой → поиск DN → bind пользователя → проверка группы)
- `services/userStore.js` — создание/обновление пользователя в БД по логину (единый аккаунт для обоих доменов)
- `services/notifications.js` — уведомления в БД + email (не блокирует запрос при недоступности SMTP)
- `services/network.js` — определение домена по подсети клиента
- `routes/auth.js` — вход (AD/локальный), выход, текущая сессия
- `routes/tickets.js` — заявки, комментарии, вложения
- `routes/modules.js` — прокси встроенных модулей (единственная точка их подключения)
- `routes/admin.js` — настройки AD-групп, список ролей, статистика
- `routes/notifications.js` — список/прочтение уведомлений
- `middleware/auth.js` — проверка сессии и роли

## Фронтенд

`public/` — интерфейс без шага сборки (чистые HTML/CSS/JS, никаких
webpack/vite/esbuild — они тянут нативные бинарники под платформу, тот же
риск, что был с `better-sqlite3`). Раздаётся тем же Express-сервером, поэтому
после `npm start` открывайте `http://localhost:3000/`.

Все запросы идут к `/api/...` через `fetch`, сессия — по cookie
(`credentials: "same-origin"`), CORS не нужен: всё на одном origin. Модули
открываются в `<iframe>` по своему `path`, то есть тоже на том же origin.

Панель администрирования хранит имена AD-групп в таблице `settings`; они
подставляются в `ldapAuth.authenticate()` при каждой проверке членства, так
что изменения вступают в силу сразу, без перезапуска сервера.

## Как устроена защита

Существенное, что стоит знать при доработке:

- **Сессия** — cookie `helpdesk.sid`: `HttpOnly`, `SameSite=Lax`, секрет из
  `SESSION_SECRET`. Идентификатор сессии пересоздаётся при входе (защита от
  session fixation). Флаг `Secure` выставляется сам, когда задан сертификат
  (см. «HTTPS»), — руками в `server.js` ничего включать не нужно.
- **Подбор пароля** — не больше 10 неудачных попыток на пару «IP + логин» за
  10 минут, дальше 429. Счётчик в памяти процесса и сбрасывается при
  перезапуске.
- **Вложения** — принимаются только из белого списка MIME-типов, не больше
  15 МБ, по одному файлу за запрос. Права проверяются **до** записи файла на
  диск, а имя папки берётся из уже проверенного числового id заявки.
  Скачиваются через `GET /api/tickets/:id/attachments/:attachmentId` с
  проверкой прав и `Content-Disposition: attachment` + `nosniff`, чтобы файл
  нельзя было исполнить в origin платформы. Каталог `uploads/` статикой
  **не раздаётся** — не добавляйте его в `express.static`.
- **Ввод** — статус, приоритет и исполнитель проверяются по белым спискам, id
  в URL обязан быть целым числом. Пользовательский текст на фронтенде выводится
  только через `esc()`; при правке `public/app.js` это правило нужно соблюдать —
  разметка собирается конкатенацией строк, автоэкранирования нет.
