# Служба заявок — Липецкстат

Backend-каркас: Node.js + Express + встроенный `node:sqlite`, аутентификация через LDAP
в двух доменах, роль администратора — по членству в AD-группе (своё имя группы на домен).

**Требуется Node.js 22.5+ (у вас Node.js 24 на сервере — подходит).** Используется
встроенный модуль `node:sqlite` вместо `better-sqlite3` — это нативный C++-аддон,
которому нужен либо готовый скомпилированный бинарник под вашу версию Node/ОС,
либо сборка на месте через node-gyp с интернетом и build-инструментами, чего на
закрытой сети нет. `node:sqlite` — часть самого Node.js, собирать ничего не нужно
(тот же подход, что и в вашем проекте реестра сертификатов).

При запуске Node будет печатать предупреждение `ExperimentalWarning: SQLite is an
experimental feature` — это ожидаемо, сам функционал стабилен, предупреждение не
мешает работе.

## Отделы и роли

Заявка привязана к отделу (ИТ / ХОЗ / ЕГРПО) — от этого зависит номер
(ИТ-0001, ХОЗ-0001, ЕГРПО-0001, у каждого отдела свой счётчик) и кто получит
уведомление о новой заявке. Роль `it` видит все заявки; `hoz`/`egrpo` видят
очередь своего отдела плюс собственные заявки в любом отделе; обычный `user`
видит только то, что сам создал или на что назначен. Роль назначается по
членству в AD-группе — три независимых группы на домен (ИТ/ХОЗ/ЕГРПО),
настраиваются в разделе "Администрирование" (только для роли `it`).

## Быстрый старт

```bash
npm install
cp .env.example .env
```

Заполните в `.env`:
- адреса контроллеров доменов А и Б (`DOMAIN_A_LDAP_URL`, `DOMAIN_B_LDAP_URL`) — лучше `ldaps://` (порт 636)
- `DOMAIN_A_SVC_DN` / `DOMAIN_B_SVC_DN` и пароли — данные сервисной учётки только на чтение (svc-helpdesk)
- `DOMAIN_A_ADMIN_GROUP` / `DOMAIN_B_ADMIN_GROUP` — точные названия групп ИТ-отдела в каждом домене

Локальный аварийный вход (на случай недоступности обоих доменов):
```bash
node scripts/set-local-admin-password.js "ВашНадёжныйПароль"
# вставьте выведенный хэш в .env как LOCAL_ADMIN_PASSWORD_HASH
```

Локальный аварийный вход — логин ОБЯЗАТЕЛЬНО начинается с "!" (по этому
символу фронтенд отличает локальный вход от доменного и не ищет такой логин
в LDAP). Есть два аккаунта: `!admin` (роль it) и `!user` (общая аварийная
учётка без прав администратора):
```bash
node scripts/set-local-admin-password.js "ВашНадёжныйПароль"
# вставьте в .env как LOCAL_ADMIN_PASSWORD_HASH
node scripts/set-local-admin-password.js "1"
# вставьте в .env как LOCAL_USER_PASSWORD_HASH
```

Автоопределение домена по подсети клиента: `NETWORK_DOMAIN_A_CIDR` /
`NETWORK_DOMAIN_B_CIDR` в `.env`. Экран входа больше не показывает вкладки
выбора домена — определяет его сам по IP запроса (`req.socket.remoteAddress`,
игнорирует заголовки вроде `X-Forwarded-For`, чтобы это нельзя было
подделать). Если сервер когда-нибудь окажется за reverse proxy — потребуется
отдельно настроить `trust proxy` и список доверенных источников.

Инициализация БД и запуск:
```bash
node db/init.js
npm start
```

Проверка: `curl http://localhost:3000/api/health`


## Структура

- `config/` — сборка конфига из `.env`
- `db/schema.sql`, `db/init.js` — схема SQLite и инициализация
- `services/ldapAuth.js` — LDAP-аутентификация (bind сервисной учёткой → поиск DN → bind пользователя → проверка группы)
- `services/userStore.js` — создание/обновление пользователя в БД по логину (единый аккаунт для обоих доменов)
- `services/notifications.js` — уведомления в БД + email (не блокирует запрос при недоступности SMTP)
- `routes/auth.js` — вход (AD/локальный), выход, текущая сессия
- `routes/tickets.js` — CRUD заявок, комментарии, вложения
- `routes/notifications.js` — список/прочтение уведомлений
- `middleware/auth.js` — проверка сессии и роли

## Фронтенд

`public/` — реальный интерфейс без шага сборки (чистые HTML/CSS/JS, никаких
webpack/vite/esbuild — они сами тянут нативные бинарники под платформу, тот же
риск, что был с `better-sqlite3`). Раздаётся тем же Express-сервером через
`express.static`, поэтому после `npm start` открывайте `http://localhost:3000/`
(или адрес сервера) в браузере — увидите рабочий интерфейс, а не `Cannot GET /`.

Все запросы идут напрямую к `/api/...` через `fetch`, сессия — по cookie
(`credentials: "same-origin"`), CORS не нужен, так как всё на одном origin.

Панель администрирования (`/api/admin/settings`) реально хранит имена AD-групп
в таблице `settings` и подставляется в `ldapAuth.authenticate()` при каждой
проверке членства — изменения вступают в силу сразу, без перезапуска сервера.

## Что дальше (не реализовано)

- Деплой как Windows-сервис через NSSM (как в вашем SMDR-проекте)
- Кэш последнего успешного входа AD на несколько часов (сейчас есть только локальный fallback-аккаунт)
- Антивирусная проверка вложений через KSC
- Разграничение видимости заявок по категориям/маршрутизация назначения
