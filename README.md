# adm-srv

Внутренняя административная платформа: служба заявок (хелпдеск) с
встроенными модулями — реестр сертификатов, журнал звонков АТС и
мессенджер организации.

## Структура репозитория

```
adm-srv/
├── helpdesk-backend/   ← платформа/админ-панель (хелпдеск + вход + прокси модулей)
├── CERTVIEWER/         ← модуль «Сертвивер» (реестр сертификатов)
├── SMDR/               ← модуль «Журнал звонков» (сборщик SMDR + веб-интерфейс)
└── MESSENGER/          ← модуль «Искра» (сервер мессенджера + десктоп-клиент)
```

Все четыре приложения — независимые Node.js-процессы, которые запускаются
и деплоятся по отдельности (каждый на своём порту), но лежат в одном
дереве проектов, потому что `helpdesk-backend` встраивает остальные три
как модули: проксирует к ним запросы через `helpdesk-backend/config/modules.js`
и `helpdesk-backend/routes/modules.js`, проверяя вход и роль пользователя
до того, как запрос уйдёт в модуль. Сами модули слушают только
`127.0.0.1` и ничего не знают про логин — см. `helpdesk-backend/README.md`.
Исключение — MESSENGER, см. ниже.

## helpdesk-backend

Платформа целиком: LDAP-аутентификация в двух доменах, роли по членству
в AD-группах, тикеты по отделам (ИТ/ХОЗ/ЕГРПО), уведомления, панель
администрирования и реестр подключённых модулей. Подробности —
`helpdesk-backend/README.md`.

## CERTVIEWER

Реестр сертификатов: разбирает PEM/DER-сертификаты, извлекает ФИО,
СНИЛС/ИНН и срок действия. Порт по умолчанию — 3101. За платформой
(`BEHIND_GATEWAY=true`) слушает только `127.0.0.1` и не спрашивает пароль
сам. Подробности — `CERTVIEWER/README.md`.

## SMDR

Журнал звонков с АТС Panasonic KX-TDE200: `Collector.Py` собирает данные
по протоколу SMDR (TCP) и пишет в SQLite, `web-node` — веб-интерфейс
(журнал, статистика, справочник добавочных), порт по умолчанию — 3102.
Веб-часть своего входа не имеет и слушает только `127.0.0.1`. Адрес АТС и
пароль SMDR задаются в `SMDR/.env`. Подробности — `SMDR/README.md`.

## MESSENGER

Мессенджер организации («Искра»): Node.js + Express + WebSocket + SQLite,
свой логин/пароль и права (`can_admin`/`can_broadcast`) — не связаны с
LDAP-ролями платформы. Веб-страница сервера — это панель администратора, а не
чат; сотрудники работают через десктоп-клиент (Electron, `desktop-client/`).
Подробности — `MESSENGER/README.md`.

Интегрирован в платформу иначе, чем CERTVIEWER и SMDR: под прокси
(`/modules/messenger`, только для роли `it`) доступна только веб-панель
администратора, и вход в неё остаётся собственный, мессенджера — второй
логин поверх входа в платформу, ничего не убирали и не встраивали в LDAP.
Десктоп-клиенты сотрудников подключаются к серверу напрямую по сети, в обход
платформы и её логина — поэтому, в отличие от остальных модулей, сам процесс
**нельзя** ограничивать `127.0.0.1`: он должен слушать реальный сетевой адрес.

**Работает по HTTPS**, и в его сертификате записано только доменное имя
(`DNS:p48-srv-adm01.rosstat.local`), без IP. Из этого следует два требования:
платформа тоже должна работать по HTTPS (см. её README), а в
`helpdesk-backend/config/modules.js` модуль адресуется **именем**, а не по
`127.0.0.1` — иначе проверка имени в сертификате не пройдёт и модуль не
откроется. Адрес можно переопределить переменной `MODULE_MESSENGER_URL`, не
трогая код.

Сертификат меняется прямо из панели мессенджера (раздел «Сертификат»), на лету
и без перезапуска — кроме одного случая: когда сертификат ставят на сервер,
до этого работавший по HTTP. При обновлении адреса сервера не забудьте
`MESSENGER/desktop-client/config.js` (`SERVER_URL`) — или пересобрать
инсталлятор клиента, или раздать сотрудникам новый адрес через Ctrl+S на
экране входа (см. `desktop-client/README-desktop-client.md`).

### Как переливать обновления из Iskra-messenger

`MESSENGER/` — не подмодуль, а копия репозитория
[`Lulzdao/Iskra-messenger`](https://github.com/Lulzdao/Iskra-messenger) с одним
отличием в раскладке: содержимое `iskra-server/` поднято на уровень выше, к
`desktop-client/`. Мессенджер продолжают дорабатывать там, поэтому обновления
приходится сливать руками. Чтобы это не превращалось каждый раз в
расследование, вот полный список файлов, которые здесь **отличаются** от
апстрима, — всё остальное берётся из него как есть:

| Файл | Что наше |
|---|---|
| `public/index.html` | Material You вместо прежнего оформления, меню — вкладками сверху; пути к API относительные (`api/...`, а не `/api/...`), иначе панель не работает под префиксом `/modules/messenger`; фон белый, как контентная область платформы |
| `desktop-client/main.js` | доверие корням из хранилища Windows, машинная политика `C:\ProgramData\Iskra\config.json` (адрес сервера по доменам, корни, аварийное разрешение http), защита от подмены адреса на http |
| `desktop-client/config.js` | `SERVER_URL` — имя и порт нашего сервера |
| `README.md`, `desktop-client/README-desktop-client.md` | порт 3103 вместо 3000 и поправленные относительные ссылки (раскладка папок здесь другая) |
| `.env.example` | наш, в апстриме его нет |

Порядок слияния: выгрузить апстрим на той точке, с которой синхронизировались
в прошлый раз, и текущий `main`, и на каждый из этих шести файлов натравить
трёхсторонний `git merge-file` (наше / старый апстрим / новый апстрим).
Остальное копируется из нового `main` без раздумий. В последний раз конфликт
был ровно один — в `removeTls()`, где апстрим переписал ту же строку, в
которой мы сделали путь относительным.

Известное ограничение: живой счётчик «сейчас в сети» на вкладке «Обзор»
панели администратора использует отдельный WebSocket на `location.origin`
(без префикса `/modules/messenger`) — платформа сейчас проксирует только
обычные HTTP-запросы, апгрейд до WebSocket через `routes/modules.js` не
прокидывается. Остальная часть панели (пользователи, отделы, права,
переписки, рассылки, файлы) работает полностью, просто без live-обновления
этого одного счётчика. Донастроить проксирование WS — отдельная задача,
если/когда понадобится.

## Разворачивание

Каждое приложение — `npm install`, затем `.env.example` → `.env` со своими
значениями (для `SMDR/Collector.Py` — `SMDR/.env`, зависимостей ставить не
нужно). `SMDR/web-node` уже настроен только под работу за платформой (своего
логина нет). `CERTVIEWER` в рабочем режиме — `BEHIND_GATEWAY=true`; при
`false` он слушает сеть и проверяет вход сам, и тогда `ADMIN_PASSWORD`
обязателен, иначе не запустится. `MESSENGER` работает со своим логином —
платформа только проксирует к нему запросы и решает, кому показывать пункт
меню.

Реальные данные (`*.db`, `uploads/`, `logs/`, `.env`,
`MESSENGER/bootstrap-admin.js`) в репозиторий не входят — см. `.gitignore`.

### Сертификаты серверов

Платформа и «Искра» стоят на одной машине и берут сертификаты из **одного**
каталога — `MESSENGER/certs/`. Второго места нет: файл `server.pfx` (плюс
`server.pass` с паролем) читают обе службы, и обе перечитывают его на лету при
замене. Доменов два, поэтому на второй домен рядом кладётся
`server.<домен>.pfx` — сервер отдаёт тот сертификат, чьё имя запросил клиент.

Загружать файлы руками не нужно: это делает панель — в платформе раздел
«Сертификаты» → «Загрузить сертификат», в «Искре» раздел «Сертификат». Полный
порядок действий (выпуск в УЦ, экспорт PFX с цепочкой, проверка, аварийная
установка с консоли, как временно выключить HTTPS) — в
[`helpdesk-backend/README.md`](helpdesk-backend/README.md), раздел «Как
поставить сертификат сервера».

Корневые сертификаты удостоверяющих центров сюда класть **не нужно**: клиенты
берут их из хранилища Windows, куда они приезжают групповыми политиками.

## Безопасность

Общие правила, которые стоит держать в голове при доработке:

- **Снаружи видна только платформа.** Модули слушают `127.0.0.1` и попадают
  к пользователю исключительно через прокси `helpdesk-backend`, который до
  проксирования проверяет вход и роль. Исключение — сервер мессенджера: к
  нему напрямую по сети подключаются десктоп-клиенты сотрудников, поэтому у
  него есть собственная аутентификация.
- **Секретов в коде и в `.env.example` быть не должно** — только пустые
  плейсхолдеры. Значения по умолчанию для паролей и секретов подписи не
  задаются: приложение либо не стартует, либо берёт случайный секрет на
  время работы процесса.
- **Разметка везде собирается конкатенацией строк** (фронтенд платформы,
  таблицы SMDR) — автоэкранирования нет. Любое значение из базы или от
  пользователя выводится только через `esc()` / `escHtml()`.
- **Права проверяются на сервере, а не только в интерфейсе.** Скрытая на
  фронтенде кнопка — не защита: соответствующая проверка должна быть в
  маршруте.
- **HTTPS разворачивает сам процесс, обратного прокси перед ним нет** — ни у
  платформы, ни у «Искры». Так не остаётся параллельного незашифрованного
  порта, про который легко забыть. Шифрование включается само, как только
  задан сертификат (`TLS_PFX` или `TLS_CERT`+`TLS_KEY`), отдельного
  переключателя нет; сессионная кука при этом сама помечается `Secure`.
  Без сертификата сервис работает по HTTP и предупреждает об этом в консоли.
- **Сертификат модуля проверяется по-настоящему.** Модуль за HTTPS адресуется
  именем из его сертификата, а не по IP. Корневой УЦ домена берётся из
  хранилища Windows (`--use-system-ca`), вне домена — через
  `NODE_EXTRA_CA_CERTS`.
- Закрытые ключи и PFX в репозиторий не попадают — см. `.gitignore`.
