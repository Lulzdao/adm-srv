# Разделение сборок Win7/Win10 и автообновления

Раздел 1 — **сделано**, описывает работающий механизм. Раздел 2 (автообновления) — **план**,
ничего из него ещё не реализовано.

## 1. Разделение сборок Windows 7 / Windows 10 — сделано

### Почему это нужно
Electron — не библиотека, а весь рантайм (Chromium + Node внутри `.exe`). Поддержку Windows 7/8.1
даёт только `electron@22.3.27` — начиная с 23 её убрали. При этом Electron 22 не получает
обновлений безопасности с середины 2023 года, а окна клиента отображают текст, присланный другими
людьми. Машинам на Windows 10 незачем сидеть на этом рантайме: им доступен современный Chromium,
где заодно не нужна часть здешних обходов (эмодзи-картинки, отключение аппаратного ускорения).

Один установщик несёт ровно один `electron.exe` — переключателем в коде это не решается.

### Как это устроено: один исходник, два конфига сборки

Первоначально предполагались **две ветки git** (`win7-lts` заморожена, `main` едет вперёд).
От этого отказались: две ветки означают ручной перенос каждого исправления, а забытый перенос
никто не замечает, пока сотрудник не пожалуется. За одну итерацию работы над проектом набралось
четыре правки (краш при выключении ПК, XSS, непрочитанное, аудит сервера) — каждую пришлось бы
переносить вручную.

Ключевое наблюдение: **версия Electron — это параметр сборки, а не свойство исходного кода.**
У electron-builder есть опция `electronVersion`: он скачивает и упаковывает именно ту версию,
которая в ней указана, независимо от того, что стоит в `node_modules`. Значит, двух веток не нужно.

```
desktop-client/build-config/
├── base.js                  общее для обеих сборок (appId, иконки, список файлов, настройки NSIS)
├── win7.js                  electronVersion 22.3.27  → dist/win7
├── win10.js                 electronVersion 43.4.1   → dist/win10
└── installer-win10.nsh      отказ установиться на Windows старше 10
```

```bash
npm run dist:win7     # установщик для Windows 7 и 8.1
npm run dist:win10    # установщик для Windows 10 и новее
npm run dist          # обе сборки подряд
```

Обе сборки всегда получаются из одного коммита — «забыть перенести исправление» физически
невозможно.

### Цена этого решения
Код обязан оставаться совместимым с Electron 22 — самой старой поддерживаемой версией. Это реальное
ограничение, но проверяемое: в `devDependencies` стоит именно 22.3.27, то есть `npm start` при
разработке запускает её, и несовместимость всплывает сразу у разработчика.

Если однажды понадобится API, которого в 22 нет — не форк ветки, а проверка наличия:
`if (someApi) { ... } else { запасной путь }`.

### Защита от установки не на ту систему
Разными именами файлов (`iskra-setup-win7-…` / `iskra-setup-win10-…`) не ограничиваемся: если
сборку win10 поставить на Windows 7, приложение просто не запустится, и разбираться будет некому.
Установщик win10 проверяет версию Windows и отказывается ставиться на более старую, объясняя, какой
файл взять вместо этого (`build-config/installer-win10.nsh`).

Обратной проверки нет намеренно: сборка win7 работает и на Windows 10, просто на старом рантайме.

### Какая сборка у сотрудника
Внизу панели настроек — строка вида `Искра 1.0.0 · сборка для Windows 7 и 8.1 · Electron 22.3.27`.
Метку проставляет electron-builder при сборке (`extraMetadata.buildTrack`), в приложение она
попадает внутри `package.json`. Нужно поддержке: обе сборки внешне одинаковы, и без этой строки
узнать, какая стоит, можно только через диспетчер задач.

### Что делать при подъёме версии для Windows 10
Меняется ровно одна строка — `electronVersion` в `build-config/win10.js`. Ориентир: Electron
поддерживает три последних мажорных выпуска, стоит оставаться в этом окне. После подъёма
**обязательно прогнать сборку на реальной Windows 10** — меняется весь рантайм, и проверить это
чем-то, кроме запуска, нельзя.

### Чего это разделение не касается
`iskra-server/server.js` от версии Electron не зависит вообще — он один на всех.

## 2. Автообновления — сделано

Инструмент — `electron-updater` (тот же вендор, что и `electron-builder`).

### Как это работает
При сборке `electron-builder` кладёт рядом с установщиком `latest.yml`: версия, имя файла и
контрольная сумма. Эту пару файлов выкладывают на сервер, клиент сверяет свою версию с `latest.yml`
и при необходимости качает новый установщик.

Раздаёт файлы сам `server.js` (`express.static` на папку `updates/`) — отдельная инфраструктура не
нужна, доступ ко всем машинам у него уже есть. Внутри — по папке на трек: `updates/win7/` и
`updates/win10/`.

### Адрес фида берётся во время работы, а не при сборке
В конфигах сборки `publish.url` есть — без него `electron-builder` не создаёт `latest.yml` вовсе —
но это **запасное** значение. Перед каждой проверкой клиент подставляет адрес заново, исходя из
того, куда он реально подключён (`updateFeedUrl()` в `main.js`).

Иначе получилось бы так: адрес сервера можно поменять на конкретной машине по Ctrl+S, а при
переезде сервера (например, при переходе на https и доменное имя) он меняется у всех — и клиент продолжал бы искать
обновления там, где сервера уже нет. То есть сломался бы ровно тот механизм, которым это чинят.

Трек в адрес подставляется тот же, что и в метке сборки: `…/updates/win7` или `…/updates/win10`.
Перепутать их нельзя — сборка для Windows 10 несёт Electron, который на Windows 7 не запускается.

### Обновление не прерывает работу
Обсуждавшийся ранее принудительный перезапуск по таймеру отброшен: оборвать человека посреди
разговора хуже, чем поставить обновление на день позже. Вместо этого:

- скачанное обновление ставится **при обычном выходе** из приложения (`autoInstallOnAppQuit`);
- в настройках показывается состояние и кнопка «Перезапустить и обновить» — если человек готов
  прямо сейчас;
- флажок «Обновлять автоматически» управляет только загрузкой; при выключенном обновление
  скачивается по кнопке.

Ошибки проверки показываются в настройках, а не глотаются: молча не обновляющийся клиент — это то,
что обнаруживают через полгода.

### Как выпустить обновление

### Открытые вопросы

**Подпись кода.** Платного сертификата нет — Windows SmartScreen предупреждает при установке
каждого нового `.exe`. Автообновление это не ухудшает и не решает.

**HTTPS со своим удостоверяющим центром — решено.** Проблема была в том, что `electron-updater`
работает через сетевой стек Node, а тот не читает хранилище сертификатов Windows: групповые
политики на него не влияют, и после перехода сервера на https обновления перестали бы работать
(та же беда у отправки файлов через `httpPostBuffer`). Исправлено одним приёмом для обоих —
корневой сертификат домена вшит в сборку и добавляется в доверие Node при старте, см.
`trustOrganizationCa()` в `main.js` и раздел про HTTPS в
[README-desktop-client.md](README-desktop-client.md).
