# Концепт: разделение сборок Win7/Win10 и автообновления

Статус: **план, ничего из этого ещё не реализовано**. Записано, чтобы не потерять решение,
принятое в обсуждении — когда будем делать, можно смело редактировать/уточнять прямо здесь.

## 1. Разделение сборок Windows 7 / Windows 10

### Почему это вообще нужно
Electron — не библиотека, а весь рантайм-шелл (Chromium + Node внутри .exe). Поддержку Windows 7
даёт только `electron@22.3.27` (последняя версия с поддержкой Win7/8.1, см.
`README-desktop-client.md`) — дальше Electron сам обрубил Win7. При этом Windows 10 может уезжать
на свежие версии Electron сколько угодно: новый Chromium, патчи безопасности, потенциально лучшая
поддержка эмодзи/шрифтов "из коробки" (часть костылей в этом проекте — как раз обходы того, чего
нет в старом Chromium на Win7).

Это не история про фича-флаги в одном codebase — один установщик всегда несёт ровно один конкретный
`electron.exe`. Значит, разделение — это **два независимых трека сборки**, а не переключатель в коде.

### Как это будет выглядеть
- **Две git-ветки**, не два файла конфига в одной:
  - `win7-lts` — заморожена на `electron@22.3.27`. Никаких новых фич, только критические фиксы,
    которые сознательно cherry-pick'аются сюда после проверки, что не тянут API, которого нет
    в Electron 22.
  - `main` (или `win10`) — свободно поднимает Electron дальше. При апгрейде мажорной версии
    возможны точечные правки в `main.js` (deprecated BrowserWindow-опции, IPC), рендерер
    (HTML/CSS/JS) почти наверняка переедет без изменений.
- **Сервер (`server.js`) один на всех** — от версии Electron клиента вообще не зависит, это просто
  Express+WS-бэкенд. Разделять нужно только `desktop-client/`.
- Два разных установщика с разными именами (`mini-messenger-setup-win7-x64.exe` /
  `...-win10-x64.exe`), чтобы IT не перепутали, кому что раскатывать.
- Релизный ритм тоже разный: `win7-lts` — редкие, тщательно проверенные "стабильные" релизы;
  `win10`/`main` — можно катать активнее.

## 2. Автообновления

### Инструмент
`electron-updater` (тот же вендор, что и `electron-builder`, уже используется для сборки .exe).

### Что происходит при сборке новой версии
`electron-builder` с `publish: { provider: 'generic', url: '...' }` в конфиге на выходе, кроме
`.exe`, кладёт ещё `latest.yml` — версия, имя файла, SHA512-хеш. Эту пару файлов нужно выложить
по HTTP там, откуда клиенты смогут её скачать.

### Где хостить
Не нужен отдельный сервер — у `server.js` уже есть доступ ко всем 200 машинам. Добавить
`express.static()` на папку `updates/` и класть туда файлы после каждой сборки (руками через SCP
или шагом в CI). Никакой новой инфраструктуры.

### Что в самом клиенте (`main.js`)
`autoUpdater` из `electron-updater`:
- `checkForUpdates()` — сверяет версию с `latest.yml`.
- события `update-available` / `update-not-available` / `download-progress` / `update-downloaded` —
  пробрасываются в рендерер через IPC, показываются тостом/модалкой в настройках.
- `quitAndInstall()` — закрывает приложение и тихо (без диалогов Windows, NSIS это умеет) ставит
  обновление.

### UI (настройки, профиль пользователя)
- Кнопка **"Проверить обновления"** → `checkForUpdates()` → если есть новее — "Доступна версия
  X.X.X — Установить?" → `quitAndInstall()`.
- Чекбокс **"Автообновления"** — если включён, при найденном обновлении сразу докачивает и ставит
  без вопроса (с уведомлением "перезапуск через 30 сек", чтобы не оборвать человека посреди
  работы). Если выключен — только проверка по кнопке, всегда со спросом перед установкой.

### Связка с разделением веток (пункт 1)
У каждой ветки — свой URL фида (`/updates/win7/latest.yml` и `/updates/win10/latest.yml`), зашитый
на этапе сборки. Иначе Win7-клиент рано или поздно попробует накатить Win10-сборку с несовместимым
Electron и сломается.

### Открытый вопрос
Нет платного сертификата code-signing — Windows SmartScreen будет ругаться на каждый новый .exe
(как ругается сейчас на первую установку). Автообновление это не ухудшает и не решает; если важно —
обсудить отдельно, когда дойдём до реализации.
